# OCR sidecar runtime deps. Pinned to known-good versions so a
# `docker compose build` in 6 months produces the same image. Bump
# intentionally with a smoke test against the warmup image.
#
# # Engine choice: RapidOCR (not PaddleOCR)
#
# We originally pinned paddlepaddle + paddleocr. PyPI removed the
# 2.5.x and 2.6.0/2.6.1 wheels (only 2.6.2 and 3.x remain for
# Python 3.11), and the surviving 2.6.2 wheel segfaults on import
# under x86_64 emulation on Apple Silicon (both QEMU and Rosetta).
# Paddle ships no Linux arm64 wheel, so any M-series dev hits this.
#
# RapidOCR uses the SAME PP-OCRv4 detection + recognition models,
# just exported to ONNX. The models are byte-identical to what
# PaddleOCR ships; only the runtime differs (onnxruntime vs paddle's
# own inference engine). onnxruntime publishes manylinux + arm64
# wheels, so the sidecar builds and runs natively on every host
# arch without an emulation layer.
#
# Detection quality is unchanged. The API surface in app.py adapts
# RapidOCR's `engine(img) → ([(quad, text, conf), ...], elapse)`
# call into the same per-language engine cache the Go side expects;
# /ocr/* and /layout/* response shapes are byte-identical to what
# the prior PaddleOCR build returned.
#
# Multi-language note: rapidocr-onnxruntime ships English + Chinese
# PP-OCRv4 mobile models out of the box. For Hindi/Tamil/etc., the
# operator drops the model files into /app/models and points at them
# via env vars (see app.py engine cache). Same approach Paddle took
# with /root/.paddleocr/ — just explicit paths instead of magic
# language codes.
